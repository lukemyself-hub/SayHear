# G2 v5 高 omission 率：证据、可能根因与下一版实验

> 状态：研究输入，非实施契约；2026-09-24。仅分析已冻结的 v5 校准和第一方资料，不运行 Provider，也不改变 v5 结果。下文的“因果假设”均需在新版本中验证。

## 结论

第二套校准的 31 个可执行正例机会只产生 1 次完整 `emit`（3.2%）。四个正例 family 中，Open Loop 为 1/8，Memory 为 0/7，stateful 为 0/8，competing pool 为 0/8；另有一条预声明的 `no_genuine_opportunity` 负例实际 `emit`。这些数字来自 [v5 round 2 的原始 treatment ledger](../../eval/continuation-acceptance-1a3b/run-v5-calibration-2/treatment-ledger.json)、[calibration report](../../eval/continuation-acceptance-1a3b/run-v5-calibration-2/calibration-report.json) 和 [verification](../../eval/continuation-acceptance-1a3b/run-v5-calibration-2/verification.json)。这是“生产机会窗口内 Provider 最终输出偏向 omit”的直接证据；它本身不能把偏向唯一归因于模型、prompt 或样本。v5 的两轮校准上限已用尽，下面的实验均属于**新版本**。

## 已确认的行为与因果假设

| 观察与一手证据 | 因果解释的边界 |
| --- | --- |
| 在第二套校准的正例中，Open Loop 的 7 个 omit 分为 `timing_not_natural` 6 次、`duplicates_main_response` 1 次；Memory 的 7 次 Provider 调用分为 duplicate 5 次、no-genuine 2 次；stateful 为 timing 4、no-genuine 2、duplicate 2；competing 为 duplicate 6、no-genuine 2。逐回合数据见 [ledger](../../eval/continuation-acceptance-1a3b/run-v5-calibration-2/treatment-ledger.json)。| `insufficient_grounding` 并非正例失召回的主因；盲目补充更多历史事实不太可能直接解决此轮失召回。 |

| [capture 时钟](../../eval/continuation-acceptance-1a3b/run-v5-capture.ts) 从 `2026-09-23T00:00:00Z` 开始，洛杉矶当地仍是 9 月 22 日 17:00。[第二轮 Open Loop fixture](../../eval/continuation-acceptance-1a3b/fixtures-v5-calibration-2/positive_open_loop.json) 中，英文及 code-switch 的截止语义却是“9 月 23 日前确认”；[ledger](../../eval/continuation-acceptance-1a3b/run-v5-calibration-2/treatment-ledger.json) 显示这些 Loop 已从 `00:00Z` 进入选择资格。其中三个洛杉矶场景返回 `timing_not_natural`，另有一个在同样的提前时点 `emit`。| **已确认的输入/门禁时区不一致**：候选在当地截止日到来前就进入表达判断；模型的 timing omit 有充分理由，提前 emit 反而值得人工检查。中文场景当地为 9 月 23 日 08:00，但“当天前确认”是否应在当天早晨追问仍有语义歧义。不能将六次 timing omit 全归咎于模型保守。 |
| [第二轮 Open Loop 历史 Event](../../eval/continuation-acceptance-1a3b/fixtures-v5-calibration-2/positive_open_loop.json) 被记录为用户原话，却普遍写成 `You contacted ...` / `你联系了...`，而不是用户明确说“我联系了...”。[v5 prompt](../../packages/ai/src/one-a-3b-role-providers.ts) 把 `sourceUserText` 视为直接 User Evidence，并只解释第一人称为用户。[冻结主回应](../../eval/continuation-acceptance-1a3b/run-v5-calibration-2/continuation-on.json) 的 `ol-004` 至 `ol-006` 还出现“我联系不了机构”之类主体澄清；八个 Open Loop 场景的第一回合主回应都已提到该事项。[capture 时钟](../../eval/continuation-acceptance-1a3b/run-v5-capture.ts) 在场景回合之间只按调用次数前进秒数，没有模拟跨日等待。| **已确认的证据叙述与后续语用干扰**：历史文本的说话人不自然，主回应有时将“你”与助手能力混淆；紧接着下一回合再提刚刚提过的事项容易显得重复。无法从现有结果单独估计每项对 omit 的贡献。下一版应使用自然的第一人称用户陈述、明确主体与当地时窗，模拟可追溯的时间间隔，并检查前一回合主回应是否已主动提及 target。 |
| [v5 表达 prompt](../../packages/ai/src/one-a-3b-role-providers.ts) 在同一段中要求判断机会、重复、时间、身份、证据、措辞和整个组合回答，并反复列出 `omit` 条件；正面可执行的 `emit` 判定流程及边界示例很少。[Provider 适配器](../../packages/ai/src/one-a-3b-role-providers.ts) 将整个 request 序列化为一条 JSON user message。| **待验证假设**：多个含糊标准叠加，使短而低风险的 omit 成为模型默认选择；也可能使 duplicate/timing 的语义边界漂移。Anthropic 第一方文档建议为复杂输入分隔上下文、列清顺序，并用贴近任务且覆盖边界的示例；这是可测试的方法，不能当作该 DeepSeek 运行失败的已证实原因。[Anthropic prompting docs](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/prompt-templates-and-variables)、[context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。 |
| [v5 pin](../../eval/continuation-acceptance-1a3b/pins-v5.json) 使用 `deepseek-v4-flash`，实际 snapshot 为 `deepseek-flash`，`reasoningEffort: none`、temperature 0.4、`json_object`。DeepSeek 官方说 `none` 关闭思考，temperature 在非思考模式生效；JSON 模式保证的是有效 JSON，并非内容判断正确。[DeepSeek Responses API](https://api-docs.deepseek.com/api/create-response/)、[thinking mode](https://api-docs.deepseek.com/guides/thinking_mode/)、[JSON Output](https://api-docs.deepseek.com/guides/json_mode/)。| **待验证假设**：该模型和 effort 对多条件语义裁决不够稳定；但目前没有同输入、同主回应的模型或 effort 对照，不能认定“Flash 太弱”或把温度 0.4 当成根因。无失败/截断主证据时，也不应把 token cap 当作解释。 |
| `duplicates_main_response` omission 探针是 3/3，其他三种 reason 只有 1/3、2/3、2/3，且 `omit-01` 在负例上 `emit`。[report](../../eval/continuation-acceptance-1a3b/run-v5-calibration-2/calibration-report.json)。| 模型并非一律保守；它同时有错放风险。只用“多 emit”衡量改进会损坏精度。 |

`duplicates_main_response` 的 3/3 只是 **typed reason 与预声明标签相同**，不等于三条语义均正确。例如 `omit-05`、`omit-06` 的冻结主回应没有提到各自的木勺、灯笼 target，却返回 duplicate；正例 `mem-004`、`mem-006`、`mem-007` 和 `comp-004` 也有类似迹象。`omit-03` 预声明 no-genuine，却返回 timing；其当地时钟仍早于历史文本的截止日期。这些对照见 [omission fixture](../../eval/continuation-acceptance-1a3b/fixtures-v5-calibration-2/omission_contract.json)、[冻结主回应](../../eval/continuation-acceptance-1a3b/run-v5-calibration-2/continuation-on.json) 和 [ledger](../../eval/continuation-acceptance-1a3b/run-v5-calibration-2/treatment-ledger.json)。因此 reason code 需要盲审语义，不能当作真实病因标签。

## 在保持精度下提高召回率的实验顺序

1. **先建立逐例错误清单。** 对 31 个可执行正例和 12 个 omission 探针独立标注：机会是否真的自然；冻结主回应或前一回合是否覆盖同一 target；Open Loop 的主体、当地时窗和未知进展是否清楚；能否写出一条合格且不重复的短句。标注员应只看冻结输入和主回应，先不看 Provider reason。将漏召回分为样本误标、主回应占用、Provider 错判、合格表达无法写出。这样才能区分可修的 prompt 问题与真实的不可追加场景。人工复核只作诊断，不回写 v5 的 1/31 分母。评测应覆盖详细案例和边界，且把开发集与保留集分开；见 [Anthropic evaluation guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) 与 [prompt engineering case study](https://www.anthropic.com/news/prompt-engineering-for-business-performance)。
2. **先修下一版输入契约，再做模型对照。** 预注册前把用户原话写成明确的第一人称或有姓名的第三方陈述；以 session 时区解释日期，区分“截止日刚到”与“截止日已过”，并记录确定性的 `before / in_window / after` 时间状态。正例分别覆盖真正的问候、开放开场和自然空档，避免重复使用“让我安静／别催”模板；同时保留这类话语作负例。主回应若在前一回合已提及 target，应单列为重复风险场景。全部输入在首次 Provider 调用前冻结，不能依据结果挑样本。[产品规则](../product/15-conversation-behavior.md) 要求只在真实机会使用目标、正确处理时窗和主体。
3. **只在新版本中对固定输入做一次性对照实验。** 冻结原主回应、当前 Event、候选集、确定性胜者、时间与 session 时区；比较 baseline 和候选表达 prompt。每一配置对每一场景只取一次语义结果，记录完整 `emit | omit`、reason、实际提交、所有硬门禁；开发集用于改 prompt，独立保留集用于确认。不能把同场景多抽几次择优当作生产召回，也不能把 v5 的失败场景移出正式分母。
4. **将 prompt 改成有优先级的裁决表，并给出正反边界例。** 先检查硬条件（target 身份/证据、时间、主回应普通问句和语义重复），再看组合回答是否自然；若条件满足，要求产出一条 target 专属、非重复、简短表达；若不满足，使用精确定义的 omit reason。给出英文、中文、code-switch 的 emit 和 omit 对照示例，特别覆盖“主回应只是泛化邀请并未覆盖 target”“主回应明确点名 target”“用户要安静且主回应已承诺不问”“有明确 Open Loop 未知结果”这些当前混淆边界。保持 `omit` 为合法出口，且不改动确定性选择器与 fail-closed 门禁。此方案的依据是现有 prompt 的结构与 [Anthropic 的具体、分步及示例建议](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/prompt-templates-and-variables)；有效性仍需实测。
5. **单独测模型和 reasoning effort。** 在完全相同的冻结输入、相同 prompt 下，比较当前 Flash/none、Flash/low 或 high，以及经过授权和完整 pin 的替代模型；度量召回率，同时看每个 omission reason、负例 `emit`、身份/时窗错用、整体回复突兀及中文问句。DeepSeek 官方说明 `reasoning.effort` 可在 Responses API 使用，`none` 关闭思考；这只支持“值得对照”，不支持“提高 effort 必然提高召回”。[DeepSeek Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)。
6. **若单段决策持续漂移，再试生成后核验。** 第一阶段基于既定 target 提出至多一条具体表达；第二阶段用可审计的证据/重复/时机核验，失败即 omit。两阶段属于**一个预先声明的语义决策流程**，不能在第一阶段 omit 后重采样或换 target。先做离线对照，证明正例召回提高且负例错放、保护类、时间和身份门禁均不退步，再考虑生产实现。Anthropic 将 prompt chaining 描述为复杂任务的候选方法，但不保证此任务收益；见 [第一方说明](https://www.anthropic.com/news/prompt-engineering-for-business-performance)。

提高召回的目标应是找到更好的操作点，同时约束错误 `emit`。一般分类理论中，降低阈值可增加召回，也可能引入假阳性；因此任何“放宽 omit”的方案必须同时报告精度及负例错放，而不能只看 `emit` 数。[scikit-learn 第一方 precision-recall 示例](https://scikit-learn.org/stable/auto_examples/model_selection/plot_precision_recall.html)。在 SayHear 的契约里，错误 `emit`、负例 `emit`、确定性硬门禁失败依然不可由召回或 pairwise 偏好抵消；见 [ADR-0114](../adr/0114-low-fatigue-pairwise-evaluation-sampling.md)。

## 不应直接采取的捷径

- 不按 v5 已观测结果挑选正式样本、不把 typed omit 改写为 emit、不对一个回合反复采样择优；这些做法破坏预注册和一次语义结果契约。[ADR-0114](../adr/0114-low-fatigue-pairwise-evaluation-sampling.md)。
- 不为了召回修改主回应、语义重排确定性 target、忽略用户收束 cue、或把模糊身份/未来时窗当已发生；这些会改变生产边界及增加错误 `emit`。[v5 prompt 与契约](../../packages/ai/src/one-a-3b-role-providers.ts)、[ADR-0136](../adr/0136-1a3b-model-pins-are-evidence-outputs.md)。
- 不假定 JSON schema、较高 temperature 或更高 effort 能直接修正语义分类；官方文档只说明这些参数的格式和运行机制。若要比较，它们必须作为新的独立配置和完整 pin 被测量。[DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/)、[Responses API](https://api-docs.deepseek.com/api/create-response/)。
