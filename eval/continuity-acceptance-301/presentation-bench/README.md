# 呈现基准（presentation-bench）

## 这是什么，不是什么

一次性的**设计用基准**，用来选「历史原文与更正在模型上下文里怎么摆」。

- 它**直接调用 Provider**（OpenCode Go 上的 DeepSeek V4.1 Flash），**绕过了 SayHear 的对话路径**：没有 Decision、
  没有检索、没有 Context Compiler、没有 Egress、没有提交。
- 所以它的结果**只能用来选呈现结构，不是验收证据**。选出的结构落到产品里之后，仍要走
  `pnpm acceptance:continuity … --mode real-model` 的真实路径验证。
- 样本取自 holdout 案例，已被看过两轮；评审人是搭工具的同一个 Agent，要点检查只是正则粗筛。

## 用法

```bash
# 只看某个布局实际会发出的请求体，不调用任何模型
node eval/continuity-acceptance-301/presentation-bench/run.mjs --layout V2 --fixture H12-work --dry-run

# 跑一格（每格默认 3 次）
node eval/continuity-acceptance-301/presentation-bench/run.mjs \
  --layout V2 --fixture H12-work --repeat 3 --round adhoc \
  --provider-credential-file /path/to/env-file

# 跑全矩阵（全部布局 × 全部 fixture；有更正的 fixture 再交叉两种更正呈现）
node eval/continuity-acceptance-301/presentation-bench/run.mjs \
  --matrix --correction a,b --repeat 3 --round r1 --provider-credential-file /path/to/env-file

# 汇总
node eval/continuity-acceptance-301/presentation-bench/summarize.mjs --round r1 --write
```

凭据：只从 `--provider-credential-file` 指向的文件里读 `OPENCODE_GO_API_KEY` 这一行，只放进请求头，不打印、不落盘。

花费：每次调用按账本的保守单价（峰值价、输入全部按未命中缓存）计入 `results/spend.json`，到 `--cap-usd`（默认 1.5）
就不再发起新调用；每次命令结束向 `../cost-ledger.json` 追加一条（请求数与 token 合计），逐次明细在
`results/<round>/calls.jsonl`。

## 文件

| 文件 | 作用 |
| --- | --- |
| `extract-fixtures.mjs` | 从原型观测（`prototype-response-structure/runs/g0/<案例>/observation.json`）抽出 History Answer 调用的真实内容，存成与布局无关的 `fixtures/*.json` |
| `export-tools.ts` | 从产品代码导出 Decision 调用的函数定义（只有 V3 需要，用来复用 Decision 的前缀） |
| `layouts.mjs` | 各候选布局：同一份 fixture → 请求体 |
| `run.mjs` | 调用、计时、记录、粗筛、记账 |
| `summarize.mjs` | 按 布局 × fixture 汇总中位数与范围 |
| `results/<round>/calls.jsonl` | 每次调用一行：token、时间点、回答原文、reasoning 原文、标注 |
| `results/<round>/requests/` | 每个 布局 × fixture × 变体 实际发出的完整请求体样例 |

## Fixture

每个 fixture 是某个 holdout 回合里「回顾之后写回答」那次调用的内容：被引用的较早消息（角色、原文、说出的时刻、
更正时刻、所属 occasion）、未被引用的当前对话、当前问题、回执里的事实行与回答要求、产品原样的指令前段
（Persona、任务指令、输出格式、locale pack），以及同一回合 Decision 调用的原样请求。

| fixture | 为什么选它 |
| --- | --- |
| `H12-work` | 更正被说反；原型里这次调用推理 11,664 token |
| `H07-september` | 原文已出站却答「没法还原」；10,939 |
| `H07-party` | 找不到引用类推理；4,438 |
| `H11-older` | 同上；4,157 |
| `H04-ask` | 同上；3,703 |
| `H06-role` | 同上；1,587 |
| `H01-recap` | 对照：很长，五个主题，部分引用 |
| `H02-said` | 对照：短，原型里没有出问题 |

`checks` 是按 holdout oracle 的允许 / 禁止事实手写的正则，只作粗筛：通过不等于语义通过，未通过要人看。
`H07-party` 那次检索没有取回「取消」那条消息，所以不能要求回答说出取消。

## 布局

所有布局的 Persona、任务指令、输出格式、locale pack 都是产品原文，模型与参数同产品（不加任何推理参数）。

| 布局 | 较早原文在哪里 |
| --- | --- |
| `V0` | 现状基线：按观测原样重放（原文是普通对话轮次，时间在 Times 序号表里，更正写在回执末尾） |
| `V1` | 仍是对话轮次，每条文本第一行带就地标记与时间（本分支 `f734290` 的做法） |
| `V2` | 材料块：原文不再是对话轮次，集中成一个有边界的块，按天分组、逐条编号带时间，放在系统指令末尾；messages 只有当前对话 |
| `V3` | 工具结果形态：原样重复 Decision 请求（指令、函数、对话）作为前缀，再接一条回顾调用和一条 tool 结果，材料块在 tool 结果里 |
| `V4` | 材料块作为当前问题前面的一条独立消息 |

更正呈现（`--correction`）：

- `a`：被更正的那条就地注明「这是更正后的说法，何时更正」；更正之前写下的其他用户消息就地注明「写于该更正之前」。
- `b`：条目按「这句话写下的时刻」排序，被更正的那条出现在更正时刻的位置，并注明它替换了哪个时刻说的那条。

两种都不比较内容、不出站更正前的原文、不排除任何消息。

## 口径

- 每次重复换一个新的 `daily_session` id：Persona 前缀照常与其他请求共享（同产品），其后的内容不会吃到上一次重复的缓存。
- 只有 `V3` 在回答调用之前先发一次 Decision 请求（`max_tokens: 1`）预热前缀，模拟产品里 Decision 刚刚发过。预热调用计费。
- 并发会影响墙钟时间。**推理 token 是主指标**；墙钟时间只在同一并发设置内可比。
- 「找不到引用」标注用的正则在原型组 0 的 38 个回合上恰好命中已知的 6 次。在带标记的新布局上它会误报
  （回答草稿里的「看不到」「没看到」等也会命中），新布局的命中都经人工读过，见下文。
- 汇总与 `show.mjs` 每次按当前 fixture 和正则**重算**要点与标注，所以修正正则后旧结果不用重跑。
- 已提交的 `calls.jsonl` 以 gzip 存放，工具直接读 `.gz`。

## 结果（2026-10-11，三轮，402 次请求，记账上界 1.273 美元）

完整表格：[`results/summary-all.md`](results/summary-all.md)，各轮 `results/<round>/summary.md`。
每个布局 × fixture × 变体实际发出的完整请求体：`results/r1/requests/`、`results/r2/requests/`。

| 轮次 | 内容 | 请求数 | 记账 |
| --- | --- | --- | --- |
| smoke | V2、V3 各 1 次（确认 tool 形态与预热可用），结果未保留 | 3 | 0.004 |
| r1 | V0–V4 × 8 fixture × 3，H12 再交叉更正呈现 b；并发 4 | 159 | 0.530 |
| r2 | V5（full / lean）、V2 lean、V3 lean × 8 fixture × 3；并发 4 | 120 | 0.315 |
| r3-serial | V0–V3 × 8 fixture × 3，**串行**，用来读墙钟时间并把每格样本加到 6 | 120 | 0.424 |

### 各布局（全部 fixture 合并；更正呈现 a）

「完整规则」r1 + r3 合并，每个布局 48 次；V4 只有 r1 的 24 次。括号内是范围。

| 布局 | 推理 token 中位 | 推理 token 合计 | 完成时间中位（秒，r3 串行） | 回答说引用的内容「看不到 / 没留着」 | 要点粗筛通过 |
| --- | --- | --- | --- | --- | --- |
| V0 现状 | 3,420 [401–13,875] | 204,170（47 次） | 26.8 [5.1–105.2] | 4 / 47 | 36 / 47（另 1 次 240 秒超时） |
| V1 就地标记 | 1,001 [116–16,727] | 72,141 | 12.0 [2.5–151.5] | 0 / 48 | 46 / 48 |
| V2 材料块在指令末尾 | 506 [131–6,002] | 44,716 | 7.6 [3.3–66.7] | 0 / 48 | 46 / 48 |
| V3 工具结果形态 | 385 [26–6,151] | 33,745 | 5.6 [1.8–26.0] | 0 / 48 | 45 / 48 |
| V4 材料块作为独立消息 | 500 [35–5,728] | （只有 24 次）24,713 | （未串行测；并发 4 下 6.5） | 0 / 24 | 24 / 24 |

- 新布局未通过的要点粗筛逐条读过：全部是正则漏判或误判（H06 的「从来没跟我讲过」、H11 的「其余几天没找到」），
  语义上没有错答。V0 未通过的 11 次里：4 次是真的答「那几条说了什么我看不到 / 没留着」（H11 两次、H07 `september` 两次，
  原文其实都在请求里），3 次是 H12 沿用旧数字或把更正说反（正则另漏掉 1 次说反的，见下表），H01 一次把今天的事带进昨天，
  H04 一次漏了救生圈，其余 2 次是正则误判。
- 「看不到 / 没留着」一栏只数「说引用的原文看不到」的回答；「后来怎么样你没说过，我答不上来」这类如实的回答不算。
- 「找不到引用 / 对不上哪条是引用」类推理：V0 在 47 次里 39 次出现。新布局里正则命中的（V1 16、V2 8、V3 2）读下来
  绝大多数是误报；真实残留的犹豫只有两类，见「模型还在哪里犹豫」。
- 没有任何一次回答把标记、块标题或编号念出来（0 / 324）。

### H12：两种更正呈现的方向正确率（逐条人工读）

「方向正确」= 把 1.5 个月当现状；「复述旧数字」= 方向正确，但把 2.5 个月作为「先前说法」又讲了一遍
（oracle 的期望是不要把更正掉的内容带回来，这一项应由人裁定）。

| 呈现 | 布局 | 方向正确 | 其中复述旧数字 |
| --- | --- | --- | --- |
| 现状（更正写在回执末尾） | V0 | **1 / 5**（另 1 次超时） | — |
| a 就地说明 | V1、V2、V3（各 6）、V4（3） | **21 / 21** | 2 / 21 |
| b 按写下时刻排序 | V1–V4（各 3） | **12 / 12** | 4 / 12 |
| a + 完整规则，V5（r2） | V5（3） | 3 / 3 | 0 / 3 |
| a + 精简规则（r2） | V2、V3、V5（各 3） | 9 / 9 | **6 / 9** |

V0 的 4 次错答：两次直接把 2.5 个月当现状，两次说「后来改口 / 更正为 2.5 个月」，与原型里看到的一致。
b 把被更正的那条挪到更正日，回答里随之出现「13 号你把奖金重新讲了一遍」这类日期归属，且 V1 配 b 的推理量是 a 的三倍
（4,002 对 1,244）；回执的逐日计数也与块内分布不再一致。**a 更好。**

### 模型还在哪里犹豫（读 reasoning 原文）

1. **留在对话里的轮次要和 Times 序号表对号**（H07 `september`、H01）：「times 1-5 但我只看到……」。
2. **被问时段内的消息一部分在对话里、不在材料里**（H01：两条因预算没被引用的消息经七天背景出现在对话里），
   而规则说「只用引用的那些」。这是产品行为本身的不一致，不是呈现能解决的。
3. V3：同一批原文既在对话轮次里（Decision 的七天背景，未标记、更正也没有标）又在工具结果里，
   H12 上方差最大（515–6,151），H02 一次回答说「今天你又提了一遍」。

第 1、2 点在 r2 用 V5 试过（去掉序号表、给对话里的较早轮次各加一行时间、加一句说明对话与材料的关系），**结果更差**：
全 fixture 推理中位 833，对 V2 的 506；H01 5,644 对 3,521，H07 `september` 1,933 对 455，另有一次空回答。

### 设计原则逐条对照

| 原则 | 数据怎么说 |
| --- | --- |
| 1 身份就地可见 | **成立。** V0 → V1 只加了就地标记，推理中位 3,420 → 1,001，「看不到内容」的回答 5 → 0。 |
| 2 证据与对话分开 | **成立。** V1 → V2 / V4 再降一半（1,001 → 约 500），长案例和带当前对话的案例差距最大。 |
| 3 代码先解状态 | **部分成立。** 就地说明（a）足以把方向做对（1/5 → 21/21）。更彻底的「按写下时刻重排」（b）方向同样全对，但更容易把旧数字带回来、日期归属变乱、推理更多。 |
| 4 时间写成人读的样子，不另开码表 | **材料块内成立，推广到对话轮次不成立。** 块里按天分组加「N 天前」没有出现时间换算的推理；但把同样做法加到留在对话里的轮次（V5）反而更差。 |
| 5 指令少而不重复；共享前缀命中缓存 | **不成立。** 精简规则没有降低推理（V2：462 对 506，在噪声内），H12 上反而把旧数字带回来（9 次里 6 次，完整规则 24 次里 2 次）。V3 稳定命中约 2,048 token 缓存，但各布局首字节都在 1 秒左右，缓存没有带来可见的时延差，只省一点输入费用。 |
| 6 计数与可见内容一致 | **成立（间接）。** V0 的犹豫正是「回执说 N 条但认不出是哪 N 条」；块尾的「N in total」与编号对得上之后这类推理消失。b 破坏了逐日计数的一致。 |

### 推荐

**V2（材料块放在指令末尾）+ 更正呈现 a + 完整规则。**

- 推理量与 V3 同一档（中位 506 对 385，差距在单次运行的噪声内，H12 上 V2 更稳），远低于现状（3,420）。
- V3 的数字略好，但它要求 History Answer 重发 Decision 的整段前缀并引入 tool 消息形态：与「History Answer 是独立
  GenerationCommand、独立编译和冻结的 Context」（ADR-0094）冲突；Decision 与回答之间落地的 Correction / Forget
  必须重新过资格（#320），前缀不能原样重放，缓存收益也就不保证；同一批原文在对话里重复出现还带来上面第 3 点的误读。
  它的优势（缓存）在时延上看不出来。
- V1（本分支 `f734290` 已实现）是保底：改动最小，方向正确率相同，但推理量是 V2 的两倍，长案例上方差最大。
- V4 与 V2 相当，但把材料伪装成一条 user 消息，来源角色不干净，不建议。

落到产品里要改的地方见协调报告；这一步尚未做。本基准之后，选定的布局仍需走真实对话路径验证。

### 局限

- 每格 3–6 次，单次波动很大（同一请求推理量可差十倍）。结论依赖的是跨 8 个 fixture 一致的方向，不是某一格的数字。
- 只测了「回顾之后写回答」这一次调用，fixture 是已经发生过的检索结果；Decision 是否发起回顾、检索是否取回该取的原文不在范围内。
- holdout 已被看过；评审人是搭工具的 Agent；要点是正则粗筛。H12 的方向与新布局的失败项是逐条读的，其余没有逐条人工评审。
- V3 的函数定义取自本分支当前代码（`history-recall:v5` 的函数说明），其余指令文本取自原型在 `f179b3d` 上的观测。
