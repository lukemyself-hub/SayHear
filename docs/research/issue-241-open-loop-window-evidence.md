# Issue #241: Open Loop local window and direct User Evidence

## Diagnosis

The frozen v5 round 2 case `g2-v5-cal2-ol-002` submitted this historical *User* Event: “You contacted the Willowbrook arts center's pottery-room booking; they said they would confirm by September 23, 2026.” This is a second-person summary, not a credible first-person statement by the user. The capture clock was `2026-09-23T00:00:00.000Z`, or September 22 at 17:00 in Los Angeles. The treatment ledger records an `awaited_outcome` with `expectedStartAt` and `followupEligibleFromAt` both equal to that UTC clock. At turn 2 the Open Loop entered the complete candidate lane, won deterministic selection, acquired a reservation, and produced a committed segment and typed use asking whether the center had replied. The fixture and clock made a result due by the local September 23 appear eligible on the prior local day. The #240 ledger identifies the same problem in the other affected Open Loop and competing cases; the v5 31-case mechanical denominator and 1/31 anchor `emit` result remain unchanged.

The production path also had a narrower, reproducible defect. `validateExpectedWindow` accepted a `precision: date` pair of UTC midnights tagged `America/Los_Angeles` without checking that either instant was a local day boundary. `computeOpenLoopSchedule` then used the proposed start unchanged for an awaited outcome, and the PostgreSQL lane selected it at that instant. The new unit test first failed with `create_loop` for the v5-shaped wrong window. The corrected formation policy rejects that inconsistent proposal. For a valid date-only deadline stated as “by [date]” or “...日前确认,” the original start, exclusive end, precision, and timezone remain frozen; follow-up eligibility starts at the exclusive end, after the local deadline. A result expected *on* a date or within a bounded range remains eligible at its supported start. The formation policy also rejects a window whose timezone differs from the Evidence Daily Session timezone. For date precision, it checks the model's time phrase against the exact source User Event and checks every occurrence for an adjacent deadline cue even if the proposal omitted that cue; a missing or unmatched phrase fails closed.

`sourceUserText` is read from the exact current User Event revision through `PostgresOpenLoopRepository.readSourceEvidence`, with active Evidence, actor, version, correction, deletion, and unique-binding checks. The segment stage sends that returned text to the Provider; it does not construct a second-person paraphrase. The PostgreSQL system test now reads back the exact first-person Event text. Thus the v5 second-person wording was a synthetic input defect, while local date validation and date-only deadline eligibility were production defects. A proposal that invents a date absent from an unknown-subject Event fails formation. Date-phrase matching alone does not establish who owns an outcome; task 3 must test semantic subject grounding and typed `omit` for its unknown-subject v6 scenario.

## Verification boundary

The focused unit tests use fixed instants for Los Angeles and Shanghai bounded windows and both DST transitions. The PostgreSQL extraction test uses a controlled extraction Provider adapter and a real committed User Event. It checks eligibility on both sides of the local deadline, reads the exact source revision, then takes the resulting lane candidate through deterministic selection, reservation, and a committed typed use. The assistant text and generation records for that final commit are synthetic fixtures; expression Provider behavior and semantic subject grounding remain task 3's responsibility. An unknown-subject Event with a Provider-invented date forms no candidate. Existing system suites separately cover target-version fencing, invalidation, and Purge. Those tests must run against distinct `TEST_DATABASE_URL` and `TEST_PURGE_MARKER_DATABASE_URL`; a skipped system suite is not a pass. The handoff examples have not been run as Provider calibration or formal acceptance.
